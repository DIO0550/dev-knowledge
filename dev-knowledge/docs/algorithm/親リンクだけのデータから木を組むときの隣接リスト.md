## TL;DR

- 「各要素が親への 1 本のリンクだけを持つ」データから木を組む操作の正体は、**グラフの転置（transpose, Gᵀ）**。CLRS の演習 22.1-3 がそのもので、隣接リスト表現なら O(V+E)、隣接行列表現なら O(V²) と明記されている。
- したがって隣接リストを 1 周で組み立てるのは**定石**。`HashMap<親, Vec<子>>` は独自の工夫ではなく、MIT 6.006 が明示する「頂点が連番でないときのハッシュテーブル版隣接リスト」そのもの。
- 木は常に E = V−1 の**疎グラフ**なので、「疎なら隣接リスト」という一般則がそのまま効く。隣接行列を選ぶ余地は原理的にない。
- ただし **「naive な O(N²) だと必ず困る」は言い過ぎ**。実測では Rust の N≤3,000 で naive でも 6ms 以下。正しい主張は「**同じ実装コストで線形に書けるので O(N²) を選ぶ理由がない**」＋「N が 1 桁増えたときの悪化が非対称」。
- 入力順序（親が子より後に現れる）への非依存は、**2 パス方式**（パス1: id だけで隣接リストを作る → パス2: root から辿る）で担保する。木を組むだけならトポロジカルソートは不要。
- 循環参照は、パス2 の**訪問ノード数が全件に満たないか**を見るのが最も安く済む（追加メモリ O(1)）。
- `adjacency` はグラフ理論の用語であって特定言語の機能名ではない。

## このドキュメントの射程

- 各要素が `parent` への 1 本のリンクだけを持つデータ（frontmatter、DB の自己参照テーブル、ファイルの親子メタデータなど）から親子ツリーを組み立てる場面。
- 「隣接リストを毎回作り直すのは定石か」「naive 実装で本当に困るのか」「入力順序と循環参照をどう扱うか」という設計判断。
- 言語非依存の一般論を主軸にする。Rust 固有の実装イディオムは別記事（`rust/design/parent-child-graph-index-arena`）に分ける。

## 遭遇した問題

親リンクだけを持つデータからツリーを描くには、親 → 子の逆引きが要る。

```yaml
# b.md
parent: tasks/a.md    # 上向きの情報しかない
```

「全件を 1 周して隣接リストを組み立てる」という設計を採ったが、その前提を裏取りしていなかった。業務コード（アルゴリズム専門ではない場面）でこの組み立て方が妥当なのか、もっと素直な方法があるのか。

## 原因（なぜ逆引きが必要になるのか）

「親リンクだけを持つ木」は **parent pointer tree** という正式に名前のついた表現形式で、その定義からして子方向に辿れない。

> A parent pointer tree ... is an N-ary tree data structure in which **each node has a pointer to its parent node, but no pointers to child nodes**.
> From any node, one can traverse to ancestors of the node, **but not to any other node**.

つまり「子リストが欲しい」は表現形式を変換する話であり、その変換が**グラフの転置**にあたる。親リンクは「子 → 親」の有向辺（各頂点の出次数 ≤ 1）なので、子リストが欲しいというのは Gᵀ の隣接リストが欲しい、ということに等しい。

## 解決

### 1. 隣接リストが定石であることの根拠

**根拠 1: 転置の計算量が教科書に書いてある。** CLRS 演習 22.1-3（第 4 版では第 20 章）が、まさに転置グラフの構築を扱っている。隣接行列表現では行列を転置するので O(V²)。隣接リスト表現では「元のグラフの全リストを走査し、頂点 v のリストに u があれば転置側の u のリストに v を追加する」だけなので **O(V + E)**。

**根拠 2: 木は常に疎グラフ。** 木の同値な特徴づけの 1 つが「連結かつ辺が n−1 本」。したがって E = V−1 で、密度は (V−1)/V² ≈ 1/V。疎グラフには隣接リスト、という一般則（CLRS / CMU 15-122 / Cornell CS2112 / MIT 6.006 が一致）がそのまま適用される。

| 操作 | 隣接リスト | 隣接行列 |
|---|---|---|
| 空間 | Θ(V + E) | Θ(V²) |
| 隣接判定 `hasEdge(u,v)` | O(deg(u))、ハッシュ化すれば期待 O(1) | **O(1)** |
| 近傍列挙 `neighbors(u)` | **O(deg(u))** | O(V) |
| 全辺の走査 | Θ(V + E) | Θ(V²) |

木を組む処理でやりたいのは一貫して「近傍列挙」であり、隣接行列が唯一有利な「隣接判定」は使わない。選択の余地がないのはこのため。

**根拠 3: `HashMap<親, Vec<子>>` は標準的な実装バリアント。** MIT 6.006 は隣接リストの実装をこう説明している。

> When vertices are uniquely labeled from 0 to |V|−1, it is common to store the top-level Set Adj within a **direct access array** of length |V| ... Otherwise, if the vertices are not labeled in this way, **it is also common to use a hash table** to map each u to Adj(u).

つまり id が連番なら `Vec<Vec<Id>>`、そうでなければハッシュマップ。どちらも「隣接リスト」の範囲内で、後者を選ぶのは奇をてらった選択ではない。

この「(key, value) の列を dict of lists にまとめる」操作は、言語を問わず標準ライブラリに畳み込まれている定番イディオム（group-by / bucketing）でもある。Python の `collections.defaultdict` 公式ドキュメントはまさにこの用例を掲載しており、Rust の itertools には `into_group_map` が、Java には `Collectors.groupingBy` がある。

### 2. コード: 2 パス方式（入力順序に依存しない）

パス1 で **id しか触らない**のが要点。親ノードの実体が既出かどうかを問わないので、親が子より後に現れても壊れない。

```
# パス1: 親 -> 子 の隣接リストを作る。各要素を1回だけ見る -> O(N)
children = {}            # 親id -> 子idの配列
roots    = []
for item in items:
    if item.parent exists and item.parent in known_ids:
        children[item.parent].append(item.id)
    else:
        roots.append(item.id)   # 親なし = root

# パス2: root から隣接リストを辿って木にする。各ノードを1回だけ訪問 -> O(N)
def build(id):
    return Node(id, [build(c) for c in children.get(id, [])])

forest = [build(r) for r in roots]
```

逆に、1 パスで「親ノードのオブジェクトを探して子を突っ込む」実装は、親が未出現だと破綻するので入力順序に依存する。

避けるべき naive 版（動かないわけではないが Θ(N²)）:

```rust
// アンチパターン: 親ごとに全件走査 -> Θ(N^2)
for p in items {
    let kids: Vec<_> = items.iter().filter(|c| c.parent == Some(p.id)).collect();
    // ...
}
```

### 3. 実測: N が数百〜数千で本当に困るのか

ノード `i` の親を `[0, i)` から一様ランダムに選んだ木を生成し、**入力順序をシャッフル**（親が子より後に来る現実的な条件）して計測した。環境は Linux 6.18.5 / rustc 1.94.1（`-O`）/ Python 3.11.15。単位はマイクロ秒（構築 1 回あたり）。

Rust:

| N | naive O(N²) | HashMap O(N) | `Vec<Vec<_>>` O(N) | CSR O(N) | naive/HashMap |
|---:|---:|---:|---:|---:|---:|
| 100 | 8.2 | 5.2 | 2.5 | 0.4 | 1.6x |
| 1,000 | 680.9 | 63.9 | 24.2 | 2.5 | 10.7x |
| 3,000 | 5,986.5 | 169.0 | 93.9 | 7.7 | 35x |
| 10,000 | 63,044.1 | 575.7 | 349.1 | 37.1 | 109x |
| 30,000 | 570,201.9 | 2,079.3 | 1,160.2 | 138.1 | 274x |

Python:

| N | naive O(N²) | defaultdict O(N) | 比 |
|---:|---:|---:|---:|
| 1,000 | 18,616.0 | 92.5 | 201x |
| 3,000 | 171,539.4 | 361.0 | 475x |
| 10,000 | 2,486,624.9 | 1,577.3 | 1,577x |

読み取れること:

- **絶対時間で見れば、数百〜数千規模では naive でも実務上問題にならないことが多い。** Rust なら N=1,000 で 0.68ms、N=3,000 で 6ms。
- **ただし言語の定数倍で結論が変わる。** 同じ N=3,000 が Python では 0.17 秒、N=10,000 で 2.5 秒。スクリプト言語では破綻ラインが 1 桁以上手前に来る。
- **小 N では naive が意外と健闘する。** Rust の N=100 では naive が HashMap の 1.6 倍にすぎない。naive の内側ループは連続メモリの線形走査で分岐予測もプリフェッチも効くのに対し、ハッシュマップは 1 要素あたりの定数が重い。「漸近計算量が良い＝常に速い」ではない実例。
- **悪化の仕方が非対称。** naive は N が 4 倍で時間 16 倍、線形版は 4 倍。Rust ですら N=30,000 で naive は 0.57 秒。データ量が想定より 1 桁増えたときに静かに死ぬのは常に O(N²) の側。

**落としどころ**: 線形版の実装コストは naive とほぼ同じ（むしろコードは短い）。だから「N が小さいから O(N²) でよい」ではなく「**同じ手間で線形に書けるから線形で書く**」が妥当な結論になる。

なお「隣接リストの構築コストは O(N+E) なので、payload 生成のたびに 2 回構築しても実用上問題ない」という判断は、上の実測の範囲では支持される（N=10,000 でも 1 回 0.58ms）。ただし本当に 2 本必要かは別途検討の余地がある（後述の関連記事を参照）。

### 4. 入力順序・トポロジカルソート・循環参照

**トポロジカルソートは不要。** 「親が子より先に来る」という入力順序の仮定は、実質トポロジカル順序を入力に要求していることに等しい。2 パス方式はこの前提を外す仕掛けなので、Kahn 法を明示的に走らせる必要はない。トポロジカルソートが要るのは「親が先」に並べ替えた配列そのものが欲しい場合だけ。

**循環参照の検出。** 親リンクのみのデータは、各頂点の出次数がちょうど 1 以下の **functional graph** で、構造が強い分だけ検出が単純になる。

| 方法 | 計算量 | 備考 |
|---|---|---|
| **到達ノード数のカウント**（推奨） | O(N)、追加メモリ O(1) | root から辿った訪問数が N 未満なら、到達不能なノード群＝閉路が存在。パス2 のついでに数えるだけ |
| 各ノードから親を辿り visited セットで検出 | 最悪 O(N²)、メモ化で O(N α(N)) | union-find 併用 |
| Kahn 法（入次数 0 から剥がす） | O(V+E) | 剥がし終えて辺が残れば閉路あり |

DFS ベースなら back edge の存在が閉路の証拠になるが、親リンク由来の functional graph では「到達ノード数カウント」が最も実装が軽く、追加コードがほぼゼロで済む。

```rust
// パス2 で訪問数を数えるだけで循環参照が検出できる
let mut visited = 0usize;
let forest: Vec<TreeNode> =
    roots.iter().map(|&r| build_subtree(r, &children, &mut visited)).collect();
if visited != items.len() {
    return Err(format!("到達できないノードがある（循環参照の可能性）: {}/{}",
                       visited, items.len()));
}
```

### 5. さらに詰めるなら CSR

id が 0..N の密な整数なら `Vec<Vec<_>>` すら不要で、2 本のフラット配列に詰められる。疎行列・グラフの世界で **CSR（Compressed Sparse Row、Yale 形式）** と呼ばれる標準形式で、構築は「度数を数える → 累積和でオフセット → 詰める」の 2 パス、O(N+E)（本質的に counting sort）。実測では HashMap 比で 8〜15 倍速い。

ただし可読性と引き換えなので、ボトルネックだと計測できてから入れれば十分。

## まとめ

- 「親リンクのみ → 木」の変換はグラフの転置であり、隣接リストを 1 周で組むのが教科書どおりの定石。木は常に疎なので隣接行列を選ぶ余地はない。`HashMap<親, Vec<子>>` は標準的な実装バリアント。
- naive な O(N²) は数千規模なら絶対時間では耐えることが多い。それでも線形版を選ぶ理由は「実装コストが同じ」ことと「1 桁増えたときの壊れ方が非対称」なこと。
- 入力順序への非依存は 2 パス方式で、循環参照は到達ノード数のカウントで、それぞれ追加コストほぼゼロで担保できる。
